## 0. The rule this checklist enforces

- **Pass = a real user, clicking through the UI, achieves the goal.** "The
  request returned 200/302" is never a pass on its own. E2E-D1 (e2e-01) is the
  reference failure: `POST config.xml` worked under a CONFIGURE grant while
  `GET /configure` was 403, so no human could use the feature and every test
  was green.
- Every row is judged on **three things**: (1) what the user sees and can click
  (screenshot), (2) the server state afterwards (REST/`api/json`/CSV/store read by
  admin), (3) that the *next* step a user would take works (the link is live,
  the saved setting changes behaviour, not only the form value).
- For every setting: **saving it is not the check; its effect is.** Each
  setting row names the observable effect.
- A row that can only be verified by the script console is marked `(console)`:
  the console may *arrange* or *read* state, never perform the behaviour under
  test.
- One browser context per account per scenario (no logout/login in the same
  context). Screenshot per step: `e2e/screenshots/<ID>-<step>.png`.
- Results legend: `PASS` / `FAIL` / `BLOCKED` (+ reason) / `N/A` (+ reason).
  Evidence: screenshot names, `out/` file names, CSV lines, HTTP codes.
- Every place where following README/e2e README as written gets stuck is a
  **documentation defect** and is listed in the report, even if worked around.

## 0a. Result rubric (owner instruction, 2026-09-29, applies from B16 onward)

A row is PASS only if all five criteria hold; each is recorded separately.

| # | Criterion | ✓ means |
|---|---|---|
| 1 | **Visibility** | the button / link / field is shown only to roles that can use it; checked as each relevant role (admin, requester, approver, no-permission `nobc`, Request-only `reqonly`, Discover-only `approver-disc`, `manager`); the roles checked are listed |
| 2 | **Goal** | a user clicking through reaches the intended end state, observed on screen (and in the store / record where applicable); a 200 or a redirect is not enough |
| 3 | **Refusal UX** | when refused, the user sees why and what to do next; a bare "Access Denied", a stack trace, a generic toast or an unexplained 4xx is ✗ (E2E-D1 type) |
| 4 | **Record** | every record / notification the spec promises is present (history row, CSV cell, mail) |
| 5 | **Evidence** | cropped relevant-region screenshot with a red box, plus steps / expected / actual (`docs/reports/e2e-03.md`, `e2e/out/section-b.log`) |

Cells: ✓ / ✗ / n.a. (+ screenshot name). Rows recorded before the rubric was introduced (section 1, A, PR, B1-B15) carry
**pre-rubric** in front of their result: they were judged "a real user achieves the goal" with the evidence named in the
row, but the five criteria were not recorded separately, so the re-audit redoes them. **Re-audited 2026-09-30** (build dae675e): every such row now starts with `re-audit ·` and the five cells (V G R C E, ✓ / ✗ / – for n.a.); the full cell texts are in docs/reports/e2e-03.md (Re-audit) and e2e/reaudit/results.jsonl, screenshots in e2e/screenshots/run-3-audit/.

### How to run (short)

1. `mvn -ntp clean package -DskipTests` in the project root (when the machine is
   free). Record the plugin version string from `/pluginManager/api/json`.
2. `cp e2e/.env.example e2e/.env`, set all passwords; `e2e/scripts/reset.sh`
   then `e2e/scripts/up.sh` (fresh `JENKINS_HOME`).
3. Run section 1 pre-flight rows (E-*) first; stop if any fails.
4. Then A, B, C in order; B-sections are independent except where a row says
   "after <ID>". Profile switches (matrix -> role -> legacy) are in section 1.6.
5. Section D only after the named PRs merge.
6. Write the result into `docs/reports/e2e-03.md` (format of the e2e tester
   brief); copy the result column there, not here.
